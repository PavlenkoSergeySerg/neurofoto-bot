# A1. Бизнес-сценарий бота-брифа на нейрофото

Статус: согласован 10.09.2026. Код на этом этапе НЕ пишется (условие темы A1).
Стек будущего бота (A2+): Python 3.13, aiogram 3, SQLite, python-dotenv.

## 1. Сценарий диалога

| № | Экран / шаг | Действие пользователя | Ответ бота | Куда пишем данные |
|---|---|---|---|---|
| 1 | Вход: карточка бота, кнопка Start | Жмёт `/start` | «Привет! Соберу заявку на нейрофото: 5 вопросов, ~1 мин. Как тебя зовут?» | Новая строка applications (status=draft), tg_user_id; FSM-состояние = name; step='name' |
| 2 | Имя | Шлёт имя текстом | Сохраняет → «Как с тобой связаться? @ник в Telegram или телефон» | applications.name; step='contact' |
| 3 | Контакт | Шлёт @ник или телефон | Сохраняет → вопрос про стиль + inline-кнопки: деловой / арт / фэнтези / киберпанк / ретро / минимализм / «не знаю, подскажите» | applications.contact; step='style' |
| 4 | Стиль | Жмёт кнопку (свой текст принимается как «свой вариант») | Сохраняет → вопрос про количество + кнопки: 1 / 3 / 5 / 10 / «другое» | applications.style; step='qty' |
| 5 | Количество | Жмёт кнопку или шлёт число 1–99 | Сохраняет → «Опиши задачу или комментарий свободно. Или жми “Пропустить”» | applications.qty; step='comment' |
| 6 | Комментарий | Шлёт текст или жмёт «Пропустить» | Сохраняет → сводка всех 5 ответов + кнопки «✅ Отправить заявку» / «🔄 Начать заново» | applications.comment; step='confirm' |
| 7 | Подтверждение | Жмёт «Отправить заявку» | Шлёт владельцу (ADMIN_CHAT_ID) оформленную заявку; пользователю: «Заявка принята! Отвечу в течение 24 ч» + кнопка «Новая заявка» | applications.status='sent', sent_at; TG-сообщение владельцу |

## 2. Границы MVP

Входит: линейный сценарий из 5 вопросов; inline-кнопки для стиля и количества;
сводка перед отправкой; запись в SQLite; TG-уведомление владельцу; повторный запуск.
НЕ входит: правка отдельного поля без перезапуска; приём фото; оплата; админ-команды;
напоминания неотвечающим; мультиязычность.

## 3. Крайние случаи

| № | Случай | Поведение пользователя | Поведение бота (MVP) | Куда пишем |
|---|---|---|---|---|
| 1 | Пустой ввод | Пустое сообщение / пробелы | Шаг не меняет, повторяет вопрос с примером; 3 пустых подряд → пауза «Вернусь позже, нажми /start» | Счётчик empty_attempts в FSM; в БД не пишем |
| 2 | «Отмена» | /cancel, «отмена», «стоп» | «Остановился. Начать заново — /start» | applications.status='cancelled', cancelled_at; FSM очищаем |
| 3 | Спам / флуд | Стикеры, голосовые, поток сообщений | Нетекст: один раз «Понимаю только текст и кнопки» + повтор вопроса; флуд: 1 ответ в 3 секунды; количество — только число 1–99, до 3 повторов | Метки флуда в FSM; в БД не пишем |
| 4 | Обрыв на середине | Закрыл TG, вернулся через день; рестарт бота | При любом сообщении: есть черновик status=draft → «Продолжить с шага X» / «Начать заново»; шаг восстанавливаем из БД | applications.step, updated_at |
| 5 | Повторный /start | Жмёт /start посреди сценария или после отправки | Есть черновик → сводка + «Продолжить» / «Начать заново» (старый → status='abandoned'); последняя заявка sent → новый черновик | Новая строка applications; старый черновик 'abandoned' |

## 4. Архитектурные решения

- Источник истины — SQLite (таблица applications): шаг сценария в колонке step,
  статусы draft / sent / cancelled / abandoned. FSM aiogram — только быстрый диалог.
- Уведомление владельцу — отдельным TG-сообщением в чат ADMIN_CHAT_ID.
- Защита от двойного клика: после первого нажатия «Отправить» кнопки убираются
  редактированием сообщения, обработчик проверяет status != sent.

## 5. Контракт переменных окружения

BOT_TOKEN, ADMIN_CHAT_ID — имена в .env.example, значения только в .env (не коммитится).

## 6. Приёмочные проверки (превью тестов A2–A3)

- Пустое сообщение ×3 → пауза, шаг не сместился.
- /cancel на шаге 3 → в БД строка со status='cancelled'.
- 10 сообщений за 2 секунды → не более 1–2 ответов.
- Рестарт бота на середине сценария → предложение продолжить с того же шага.
- /start дважды подряд → не две новые заявки, а вопрос «продолжить/заново».
